The Problem

WFP Building Blocks runs as a network of independent network-members — organisations each running their own node, backend, and local database. Every member stores only the {common-identifier → proxy wallet} mappings for beneficiaries it onboarded.

When member A onboards a person and mints a wallet, and later member B assists the same person, B cannot discover that a wallet already exists. The person ends up with two wallets, breaking redemption and deduplication.

The constraint: the common identifier (National ID, UNHCR ID, Tax ID) is PII — even when hashed. It must never cross the member-to-member wire, never be stored on chain, and the beneficiary is not online to self-verify.

BBNew lets any member privately answer "does a wallet already exist for this person, and what is it?" with mathematically-enforced data minimisation: no PII on the wire, no cleartext wallet on the wire, no central server.

Cryptographic Approach

1 — VOPRF (RFC 9497, P-256/SHA-256)

A Verifiable Oblivious Pseudo-Random Function lets member B (the querier) compute a per-responder pseudonym for an identifier without the identifier ever leaving B's perimeter and without B learning the OPRF key.

  • B blinds the normalised identifier (multiplies by a random scalar on P-256) → opaque elliptic-curve point.
  • A evaluates the blinded point with its private key → evaluated point + DLEQ proof.
  • B unblinds and verifies the DLEQ proof → pseudonym raw.
  • The DLEQ proof guarantees A used the same key for all queries — preventing per-query fingerprinting.

2 — Match-oblivious Fixed-Length AEAD Lookup

B derives a 16-byte lookup tag and a 32-byte encryption key from the VOPRF output via HKDF-SHA-256. B sends only the tag to A. A always returns a fixed-length 112-byte blob:

  • Hit: real AES-256-GCM ciphertext of {"o":"M1","w":"0xabc…"} (owner + wallet, padded to 96 bytes).
  • Miss: randomBytes(112) — byte-for-byte indistinguishable from a real ciphertext.

Only B — who independently re-derived the OPRF output and thus the encryption key — can distinguish hit from miss by attempting GCM decryption. A never learns B's decision.

3 — No-Duplicate-Wallet Fan-Out

When onboarding a new beneficiary, a member first checks locally, then queries all peers in deterministic order (lexicographic memberId). If any peer returns a hit, the member adopts the existing wallet (smallest-owner wins) rather than minting a new one.

4 — Versioned Key Rotation

Each member can rotate its OPRF key. The new key version is derived deterministically from the master seed (deriveKeyPair(masterSeed, v)), and the local pseudonym table is rebuilt from the member's own cleartext ID store (which it legitimately holds). The old version enters a brief grace window then is retired — old pseudonyms become permanently unresolvable, bounding the cross-member linkage window.

5 — Concurrent-Onboarding Reconciliation

If two members onboard the same brand-new person simultaneously they may each mint a wallet. The deterministic-owner total order (lexicographic memberId) designates the authoritative wallet. Any member can run POST /admin/reconcile to call ledger.mergeWallets(loser, winner) and re-point its local mapping. With no coordinator, all members converge.

Protocol Step-by-Step

Single cross-member query: member B asks member A whether it knows a wallet for normalised identifier id.

  1. Meta fetch
    B calls GET A/meta → { activeKeyVersion, activePublicKeyB64 }. B now knows A's current OPRF public key without learning the private key.
  2. Blind
    B blinds utf8(normalize(id)) using A's public key: OprfSession.blind(pk_A, message) → an elliptic-curve point that is information-theoretically independent of id.
  3. Evaluate
    B sends POST A/oprf/evaluate { keyVersion, evaluationRequestB64 }. A evaluates with its private key and returns { evaluationB64 } plus an embedded DLEQ proof.
  4. Finalize & verify DLEQ
    B calls session.finalizeAndVerify(evaluationB64). If the DLEQ proof fails — meaning A used a different key for this query — an exception is thrown and the result is discarded.
  5. Derive tag and encryption key
    B derives tag = HKDF(raw, "BBNew/tag/v{v}", "lookup-key")[:16] and encKey = HKDF(raw, "BBNew/enc/v{v}", "wallet-wrap")[:32]. These are computed locally; only the tag crosses the wire.
  6. Lookup
    B sends POST A/lookup { keyVersion, tagB64 }. A always returns { nonceB64, blobB64 } — 112 bytes regardless of hit or miss.
  7. Decrypt (or discard)
    B attempts AES-256-GCM decrypt(encKey, nonce, blob, aad) where aad = "BBNew|{v}|{tagHex}". Authentication success → wallet found at A. Authentication failure → A has no wallet for this person. A never learns the outcome.

Packages

@bbnew/shared
Identifier normalisation (NFC, separators, scheme prefix), HKDF-SHA-256 via node:crypto WebCrypto, AES-256-GCM AEAD with fixed-length padding (WALLET_BLOB_LEN=112), lookup-tag & wallet-key derivation, Zod-validated wire schemas, wire-audit singleton.
@bbnew/voprf
RFC 9497 VOPRF wrapper around @cloudflare/voprf-ts (P-256/SHA-256). Versioned OprfKeyManager (deterministic key derivation), OprfSession client (blind / finalizeAndVerify with mandatory DLEQ enforcement).
@bbnew/ledger
Simulated blockchain. createWallet() → random 20-byte hex address. loadAssistance, redeem (underflow-guarded), mergeWallets(loser, winner) moves balance and resolves merge chains. Fully in-process; no persistence required.
@bbnew/member
Fastify 5 service per member. Routes: /meta, /oprf/evaluate, /lookup, /onboard, /admin/rotate, /admin/reconcile. Peer-client (crossMemberQuery), pseudonym-table CRUD & rotation rebuild, in-memory + JSON-snapshot repository, per-tag async mutex.
@bbnew/demo
Spins three members in-process (ephemeral ports, shared ledger, fully-meshed peers) and narrates a 7-step scenario: same person → one wallet; different person → different wallet; key rotation invalidates old pseudonyms; concurrent race converges; wire audit asserts no PII or cleartext wallet anywhere.

Usage

Prerequisites

Node.js 20+ with npm 10+. No native modules; runs entirely on Node built-ins and pure-JS packages.

Install

git clone <repo>
cd BBNew
npm install

Narrated end-to-end demo

npm run dev

Spins M1, M2, and M3 in-process, runs the full 7-step scenario with console narration, and exits non-zero on any assertion failure. Proves:

  • Same person across M1/M2/M3 → exactly one wallet, balance accumulates correctly.
  • Different person → separate wallet.
  • Key rotation at M1 invalidates old pseudonyms; dedup still works under the new key.
  • Genuine concurrent onboarding at M2 and M3 (mutex off) → mergeWallets converges to one wallet.
  • Wire audit: no raw identifier, no normalised identifier, no cleartext wallet ever appears in any cross-member payload.

Wire Audit in Tests

The wireAudit singleton (from @bbnew/shared) records every cross-member HTTP request and response in-process. Tests call:

wireAudit.setEnabled(true);
wireAudit.clear();
// ... run scenario ...
wireAudit.assertNoneLeaked(['UNHCR:AUDIT77', a.wallet], crossPred);
wireAudit.assertOnlyAllowedKeys({
  '/meta': ['memberId', 'activeKeyVersion', 'activePublicKeyB64', 'answerableVersions'],
  '/lookup': ['keyVersion', 'tagB64', 'nonceB64', 'blobB64'],
}, crossPred);

Wire allowlist: cross-member payloads (between member services) are limited to the fields above. No field outside these sets may appear between members — enforced by the wire-audit test suite.

Honest Limitations

Still processes personal data (GDPR). OPRF outputs and lookup tags are pseudonymous, not anonymous. Each member remains a data controller for its own local cleartext identifier store — that store is lawful, necessary, and never shared. The cryptography provides cross-member data minimisation, not anonymisation of a member's own records.
Offline dictionary attack. A member holding its own OPRF key can test offline whether any enumerable identifier (National ID, etc.) was ever the subject of a query against it. PII content never leaks on the wire, but the fact of a query can be inferred by the responder. Mitigated by per-member keys, key rotation, and rate-limiting — not eliminated. This is inherent to OPRFs over low-entropy inputs.
Not constant-time. @cloudflare/voprf-ts is not constant-time in JavaScript — timing side channels exist. Acceptable for a simulation prototype; documented here.
"Offline" scope is limited. No central server ✓, beneficiary not online ✓, but member-to-member connectivity is required at onboarding time (deduplication is fundamentally a communication problem). A partitioned member can only provisionally mint and reconcile later via mergeWallets — it is not true offline deduplication.
Simulated blockchain. @bbnew/ledger is entirely in-process. Wallet addresses are random non-PII hex strings. This is a deliberate scope decision, not a TODO — the cryptographic protocol is the focus.
